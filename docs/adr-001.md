# ADR-001 — Implement the TOC engine ourselves instead of wrapping an existing tool

**Status:** Accepted
**Date:** 2026-08-16
**Deciders:** Manus AI

## Context

Generating a table of contents for a Markdown document sounds trivial, but three constraints make it subtle: GitHub's anchor slugification has well-documented quirks (accent decomposition, duplicate suffixes, inline-format stripping), heading extraction must correctly skip content inside fenced code blocks and HTML comments, and the tool needs a deterministic drift-detection loop suitable for CI.

The obvious alternatives were:

1. **Wrap [markdown-toc](https://github.com/ariatemplates/markdown-toc)** — the de-facto standard, but it is unmaintained, has 200+ open issues around incorrect slugs, and pulls a Node.js toolchain into every pipeline.
2. **Use a generic Markdown parser (markdown-it / mistune)** — correct but heavy; pulling a full parser for two operations (heading extraction, link validation) adds dependency weight and parse-time variance we do not control.
3. **Shell out to an existing binary (mdtoc, bitdowntoc)** — loses the tight exit-code contract and makes embedding in Python CI scripts awkward.

## Decision

Build a small, dependency-free engine: a single-pass heading extractor in `toc.py` that tracks fence and comment state explicitly, plus a slugifier that replicates GitHub's published algorithm step for step. The engine exposes both a CLI and a Python API from the same core.

## Consequences

**Positive.** Zero runtime dependencies; the slug behaviour is pinned to a reference we control, so test fixtures can assert GitHub-identical output forever. The exit-code contract (`0`/`1`/`2`/`3`) gives CI pipelines a precise signal. The whole codebase fits in five modules and is fully type-checked under `mypy --strict`.

**Negative.** We own correctness of a parser-adjacent component: Setext headings, nested fences, and multi-line comments are all edge cases we must test explicitly. Mitigated by 84 unit tests plus 20 red-team scenarios, and by the design choice to treat fenced/comment content as opaque state rather than attempting full Markdown parsing.
