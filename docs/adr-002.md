# ADR-002 — Require explicit `<!--TOC-->…<!--/TOC-->` markers instead of guessing an insertion point

**Status:** Accepted
**Date:** 2026-08-16
**Deciders:** Manus AI

## Context

A TOC generator must decide *where* the table of contents lives in the document. Common strategies are: insert after the first heading, insert at a heading named "Contents", or require the author to mark the spot explicitly.

## Decision

DocToc requires an explicit block delimited by `<!--TOC-->` and `<!--/TOC-->`. When `generate` runs against a file that has no such block, one is appended directly after the first heading — a pragmatic fallback that still gives the author a deterministic, reviewable location.

## Consequences

**Positive.** The sync loop becomes a pure text comparison between the rendered block and the existing block: no heuristics, no drift ambiguity, and `check` can report drift without any document analysis beyond the markers. The markers are invisible in GitHub's rendered output (they are HTML comments), so authors get a native-looking TOC with zero visual noise. Rewrites are surgical: everything *outside* the markers is byte-identical before and after, which makes `git diff` trivially reviewable and keeps the tool safe for CI auto-commits.

**Negative.** Authors must add two comment lines to new documents. This is a one-time cost, and the auto-append fallback removes the pain for first runs. Tools that guess insertion points (e.g., some Markdown editors) will fight DocToc in a shared repository — mitigated by the CI gate, which simply re-syncs the block regardless of who moved it.
